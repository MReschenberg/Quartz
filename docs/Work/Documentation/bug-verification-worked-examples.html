Bug Verification — Worked Examples

Each example below traces a real, recently closed bug through the flowchart in bug-verification-flowchart. For every decision point, the example states: what was found, why that finding leads to the next step (or to a stop), and why the alternative branch was not taken.

All six examples below resolve as generic bugs — stopping at Step 1 or at Focus Management Testing. This is the most common outcome for bugs surfaced through Fable tests and AT audits: the fix is in the markup, and once you see the problem in the core tree, there is no reason to continue.

Before you open any tool

Q1 — What did the user report? Several form inputs in about:preferences (Sync, Home, Privacy pages) are announced by screen readers without any name — just the role and type. For example, a text field in the Connection Settings dialog is announced as “edit text” with no indication of what it is for.

Q2 — AT and OS? Screen readers on multiple platforms.

Q3 — Focus management bug? No. The user is reporting what the AT announces about specific elements — a naming issue, not a focus movement issue. Stay on the tree path.

Q4 — Hypothesis: If this is a generic bug, the name field in the core a11y tree will be empty for these inputs. Adjacent visible text is not wrapped in a <label for=""> element, so no name is computed.

Step 1: Check the core a11y tree

Self-check answer: I am looking for the name field on each affected input. If it is empty, the bug is in the markup and affects all ATs.

What I found: The name field is empty for each affected input. The adjacent text that serves as a visual label has no programmatic association to the input.

Decision: absent → file as generic. Stop here.

Why stop: A name that does not exist in the core tree cannot exist in any platform tree. No AT on any platform will ever announce a label for these inputs, because there is nothing for any platform tree to pick up. The fix — adding <label for=""> or aria-labelledby — changes what the core tree computes, which then propagates everywhere.

Why not Step 2: Testing a second AT would only confirm that it also fails to announce a label. It cannot tell us anything new about why the label is missing. We already know why: the name is absent from the core tree.

Filing

Scope: Desktop, no OS, no AT. Severity: S2 (significant — affects core form usability for screen reader users). access keyword: required (Settings UI is not a Disability Access module).

Example 2 — Non-descriptive button names

Bug: 2008119 · New Tab Page · S3 Category: Name present but non-descriptive — context missing from computed label

    STOP1 --> FIL["📝 Filing"]
    style PRE fill:#dbeafe,stroke:#2563eb,color:#1e3a5f
    style REF fill:#ede9fe,stroke:#7c3aed,color:#3b0764
    style S1 fill:#dbeafe,stroke:#2563eb,color:#1e3a5f
    style STOP1 fill:#dcfce7,stroke:#16a34a,color:#14532d
    style FIL fill:#dbeafe,stroke:#2563eb,color:#1e3a5f

Before you open any tool

Q1 — What did the user report? In the Topics dialog (New Tab → Personalize → Topics), multiple buttons are announced identically — “Following,” “Following,” “Following” — with no indication of which topic each one acts on. Users cannot distinguish between them.

Q2 — AT and OS? Screen reader users, multiple platforms implied.

Q3 — Focus management bug? No. The user is describing what the AT announces about each button — a naming problem, not a focus movement problem.

Q4 — Hypothesis: If this is a generic bug, the name field in the core tree will show a value (the button is not unlabeled), but the value will be only “Following” — it will not include the topic name it acts on. The label exists but lacks context.

Step 1: Check the core a11y tree

Self-check answer: I am looking at the name field. I expect it to be non-empty, but I need to check whether the value is sufficient — does it include the topic (“Following Movies,” “Following Sports”) or is it just “Following”?

What I found: name is present and reads “Following.” The button is not unlabeled — it has a name. But the name does not include the topic it acts on, making it identical to every other button in the list.

Decision: present but incorrect value → file as generic. Stop here.

Why stop: The incorrect name is what the core tree computes. Every AT on every platform will read “Following” from the same tree. The fix — adding aria-label="unfollow movies" with topic context — changes the computed name in the core tree. That change applies everywhere.

Why not Step 2: This is different from Example 1 in an important way: the name field is not empty, so you might be tempted to conclude the core tree is fine and test a second AT. But “present” does not mean “correct.” A name that lacks necessary context is a defect in the core tree, and testing a second AT would not change that — it would also read “Following.” The issue is in the markup, not the AT.

Note on this bug type: This is the subtlest case in the table. If you inspect the tree and see a non-empty name, pause and ask: is this name actually correct? Does it give a user enough information to act? If not, you are still looking at a generic bug.

Filing

Scope: Desktop, no OS, no AT. Severity: S3 (moderate — users can reach the buttons but cannot distinguish them). access keyword: required.

    style STOP1 fill:#dcfce7,stroke:#16a34a,color:#14532d

Before you open any tool

Q1 — What did the user report? When navigating to the Customize button on the new tab page, the screen reader does not announce whether the panel is expanded or collapsed. The user cannot tell whether their previous keypress opened the panel.

Q2 — AT and OS? Screen reader, platform not yet determined.

Q3 — Focus management bug? No. The user is describing missing state information from what the AT announces about the button. Focus is not lost; the announcement is incomplete.

Q4 — Hypothesis: If this is a generic bug, I will find no aria-expanded state on the button node in the core tree. A state that does not exist in the core tree cannot be reported by any AT.

Step 1: Check the core a11y tree

Self-check answer: I am looking at the states/properties section for the Customize button node. Specifically, I expect aria-expanded to be absent entirely if this is a generic bug.

What I found: The button node is present in the tree and correctly named. The states section does not include aria-expanded — the attribute is simply not there.

Decision: state absent → file as generic. Stop here.

Why stop: A state that does not exist in the core tree does not exist in any platform tree. No AT can report “expanded” or “collapsed” because neither value has been exposed anywhere in the tree. The fix — adding aria-expanded to the button element — adds the state to the core tree, and all platform trees and ATs will then have access to it.

Why not Step 2: There is nothing to test with a second AT. The information the AT would need to report the state simply does not exist yet. Testing VoiceOver after NVDA would give you the same result: silence on the state, because the state is not in the tree for either of them to read.

Filing

Scope: Desktop, no OS, no AT. Severity: S3 (moderate — users cannot confirm whether their action had the intended effect). access keyword: required.

Example 4 — Selection state and role both absent

Bug: 2036737 · IP Protection Category: Missing value and role — aria-checked and radio group semantics not exposed

    PRE["🔍 Before you open any tool"] --> REF["📋 Bug symptom reference"]
    REF --> S1["Step 1: Check core a11y tree"]
    S1 --> STOP1(["✅ STOP: File as generic (Desktop)"])
    STOP1 --> FIL["📝 Filing"]
    style PRE fill:#dbeafe,stroke:#2563eb,color:#1e3a5f
    style REF fill:#ede9fe,stroke:#7c3aed,color:#3b0764
    style S1 fill:#dbeafe,stroke:#2563eb,color:#1e3a5f
    style STOP1 fill:#dcfce7,stroke:#16a34a,color:#14532d
    style FIL fill:#dbeafe,stroke:#2563eb,color:#1e3a5f

Before you open any tool

Q1 — What did the user report? In the VPN location picker, users can navigate the location list but cannot tell which location is currently selected. Screen readers on Windows do not announce “selected,” and on macOS and Linux, no state information is announced at all when navigating or activating a location.

Q2 — AT and OS? Multiple ATs and OSes. The variation in symptoms across platforms (Windows partial, macOS/Linux none) is notable — but note: the correct response is not to start testing each platform in turn. First check the core tree.

Q3 — Focus management bug? No. The user can navigate the list; they just cannot tell which item is selected. This is a state and value announcement issue.

Q4 — Hypothesis: If this is a generic bug, the location items in the core tree will either: (a) have no role that conveys selection semantics (e.g. they are plain listitem nodes without radio or option roles), or (b) have no aria-checked or aria-selected property. The cross-platform variation in symptoms is a clue that the core tree is missing both the role and the value — different platforms and ATs may partially fill in gaps differently, which is why behavior varies.

Step 1: Check the core a11y tree

Self-check answer: I am looking at two things for each location item: the role and any value/state property (aria-checked, aria-selected). I expect both to be absent if this is a generic bug.

What I found: Location items are exposed as generic nodes without a role that conveys selection (no radio, no option). No aria-checked or aria-selected property appears. The core tree has no mechanism to communicate selection state.

Decision: role and value both absent → file as generic. Stop here.

Why stop: The cross-platform variation in symptoms might look like evidence of a platform-specific bug, but it is actually evidence of a generic one: different ATs and platforms handle missing semantics differently (some guess, some stay silent, some partially announce), which is why you get different failure modes on different systems. The root cause — no role, no value in the core tree — is the same everywhere. The fix (adding role="radio" and aria-checked to each item, and wrapping in a radio group) is a markup change that benefits all platforms at once.

Why not Step 2: Testing a second AT would confirm that it also fails to announce selection state. But we already know why — neither the role nor the value is in the core tree. A second AT test would be redundant and would not change the scope or the fix.

Why not interpret the cross-platform variation as a platform-specific signal: The fact that Windows announces partial information and macOS announces nothing does not mean this is a Windows-specific or macOS-specific bug. It means these platforms handle absent semantics differently. The consistent underlying problem is the absence of role and value in the core tree.

Filing

Scope: Desktop, no OS, no AT. access keyword: required.

Example 5 — Focus lost after button activation

Bug: 2027931 · IP Protection · S3 Category: Focus management — focus lost after activating a toggle

flowchart LR
    PRE["🔍 Before you open any tool"] --> FM["🎯 Focus Management Testing"]
    FM --> STOP1(["✅ STOP: File as generic (Desktop)"])
    STOP1 --> FIL["📝 Filing"]
    style PRE fill:#dbeafe,stroke:#2563eb,color:#1e3a5f
    style FM fill:#fef3c7,stroke:#d97706,color:#451a03
    style STOP1 fill:#dcfce7,stroke:#16a34a,color:#14532d
    style FIL fill:#dbeafe,stroke:#2563eb,color:#1e3a5f

Before you open any tool

Q1 — What did the user report? After pressing Enter on “Turn off VPN,” the VPN state changes but focus disappears entirely. Pressing Tab afterward takes the user nowhere.

Q2 — AT and OS? Keyboard navigation with screen reader (the focus loss was observed during keyboard testing).

Q3 — Focus management bug? Yes. The user pressed a button and focus was subsequently lost. This is a focus management bug. Skip the a11y tree inspection entirely. Go to Focus Management Testing.

Why skip the tree: The a11y tree describes properties of nodes — names, roles, states. It does not describe where focus lands when a button fires an event. No amount of inspecting the tree for this bug will tell us why focus disappears after activation.

Focus Management Testing

Self-check answer: The triggering action is pressing Enter on “Turn off VPN.” Expected behavior: since this is a toggle button, focus should remain on the button after activation (the button still exists — it becomes “Turn on VPN”). Focus moving away or disappearing is the bug.

Step A — Reproduce with keyboard only (no AT):

Activate “Turn off VPN” with Enter. Press Tab. Focus is lost — Tab goes nowhere.

What this means: The focus loss reproduces with keyboard only, without any AT active. This is a code-level bug. It is not caused by the AT’s focus handling — it is caused by how the component manages focus when the button fires. All keyboard users, including all screen reader users on all platforms, are affected.

Decision: reproduces keyboard-only → file as generic. Stop here.

Why stop: A focus management bug that reproduces with keyboard only is definitionally not AT-specific or platform-specific. The fix (keeping focus on the toggle button after state change) is in the JavaScript event handling. That fix will benefit all users equally.

Why not open the a11y tree: The tree would show the button node with correct name, role, and state. Everything looks fine in the tree — because the issue is not with what the node exposes, but with what happens to focus when it is activated. The tree does not model event-driven focus movement.

Why not go to Step 2: There is no AT-specific behavior to test. The bug already reproduces without any AT. Testing VoiceOver or NVDA would confirm that they also experience focus loss, but that would not tell us anything new about scope or cause.

Filing

Scope: Desktop, no OS, no AT. Severity: S3 (keyboard users lose their place in the interface; must navigate back from the top). access keyword: required (IP Protection is not a Disability Access module).

    style STOP1 fill:#dcfce7,stroke:#16a34a,color:#14532d
    style FIL fill:#dbeafe,stroke:#2563eb,color:#1e3a5f

Before you open any tool

Q1 — What did the user report? When navigating the browser toolbar with VoiceOver, a “Google, pick a search engine, button, popup collapsed” is announced — but this button is not visible on screen. When activated, it opens a dropdown even though it appears hidden.

Q2 — AT and OS? VoiceOver on macOS. (But note: the diagnosis will determine whether this is macOS-specific.)

Q3 — Focus management bug? No. The user is reaching a control that announces itself — this is not about where focus goes after an action. It is about a control that should not be reachable being in the tree.

Q4 — Hypothesis: This is the inverse of the usual inspection question. I am not looking for something absent — I am looking for an unwanted presence. If this is a generic bug, the search mode switcher will appear in the core a11y tree without aria-hidden applied to it or any of its ancestors. Its presence in the tree (without hiding) means every AT on every platform can reach it.

Step 1: Check the core a11y tree

Self-check answer: I am looking for the search mode switcher node. I expect to find it present in the tree when it should not be. I am also checking whether aria-hidden or any equivalent hiding mechanism appears on this node or its ancestors.

What I found: The search mode switcher node is present in the core tree. There is no aria-hidden on it or its ancestors. Visually it is hidden (via CSS), but from the tree’s perspective it is fully accessible.

Decision: element present in tree when it should be hidden → file as generic. Stop here.

Why stop: The absence of aria-hidden is a property of the core tree — it is the same on every platform. Any AT on any OS that queries the core tree (and all of them do) will find this node and expose it. The bug is not a quirk of VoiceOver’s behavior; VoiceOver is correctly reporting what it finds. The fix — adding aria-hidden to the switcher when it is visually hidden — changes what is in the core tree, and all ATs on all platforms benefit.

Why not treat this as a macOS/VoiceOver-specific bug: The reporter used VoiceOver on macOS, but that is only because that is the AT they were testing with. NVDA on Windows would also find and announce this node — it is in the core tree, which all ATs consume. The symptom was discovered on macOS, but the scope is not macOS. This is the most common reason to over-scope a bug: the platform of discovery is not the same as the platform of the bug.

Why not Step 2: The node is in the core tree without aria-hidden. Testing a second AT would confirm that it also reaches the node — but that confirms what we already know. The fix is in the markup.

Filing

Scope: Desktop, no OS, no AT. Severity: S3 (screen reader users encounter phantom interactive controls with no visual counterpart, which is confusing and unpredictable). access keyword: required.

Bug: Recent Activity toggle — Settings Redesign Fable test Category: AT-specific — Voice Control on macOS cannot locate the node; VoiceOver on macOS can

    style S2 fill:#dbeafe,stroke:#2563eb,color:#1e3a5f
    style STOP2 fill:#dcfce7,stroke:#16a34a,color:#14532d
    style FIL fill:#dbeafe,stroke:#2563eb,color:#1e3a5f

Before you open any tool

Q1 — What did the user report? A Fable participant using Voice Control on macOS said “show numbers.” The Recent Activity toggle did not receive a number, but every other toggle above it in the list did. The participant could not activate it by number or name.

Q2 — AT and OS? Voice Control on macOS.

Q3 — Focus management bug? No. The user is describing an element that Voice Control cannot locate at all — it doesn’t appear in the numbers overlay. This is about whether the element is present in Voice Control’s tree, not about where focus goes after an action.

Q4 — Hypothesis: If this is a generic bug, the toggle node will be absent from the core tree entirely, which would explain why VC can’t find it. If the node IS in the core tree, the bug is somewhere downstream — in the macOS platform tree or in how Voice Control specifically queries that tree.

Step 1: Check the core a11y tree

Self-check answer: I am looking for the Recent Activity toggle node. If absent → generic. If present with correct name, role, and state → not generic, continue.

What I found:

  • Node is present.
  • Name: “Recent activity” ✓
  • Role: button ✓
  • State: aria-pressed: true ✓

Everything the AT needs is in the core tree.

Decision: all properties correct → not generic. Continue to Step 2.

Why not stop: If the name, role, and state are all present and correct, the markup is not the problem. The core tree has what Voice Control needs; something further down the stack is failing to surface it.

Why not look further: Checking other properties like aria-describedby or running the automated checker would not tell us why VC can’t number this element. The presence question — is the node in the tree? — is answered. Move on.

Step 2: Test with a secondary AT on the same platform

Self-check answer: VoiceOver is the other major AT on macOS and it also reads the macOS platform tree. If VoiceOver can reach the toggle, the macOS platform tree is intact and the failure is specific to Voice Control. If VoiceOver also cannot reach it, the macOS platform tree itself is broken for this node.

What I found: Navigate to the Recent Activity toggle with VoiceOver. VoiceOver announces “Recent activity, toggle button.” VoiceOver can reach it and reads both the name and role correctly.

Decision: second AT succeeds → AT-specific. Stop here.

Why stop: VoiceOver and Voice Control both consume the macOS platform tree. VoiceOver can reach this node, which means the macOS platform tree has the information. The failure is specific to how Voice Control queries that tree — Voice Control asks different questions about the platform tree than VoiceOver does, and its particular query is not returning this node. The fix belongs with how Voice Control handles this type of node, not in Firefox’s markup or platform layer.

Why not Step 3: Testing Windows would be redundant. We already know the macOS platform tree is correct (VoiceOver proves this). Filing as macOS + Voice Control is the right scope — there is no reason to believe Windows users are affected.

Filing

Scope: macOS, Voice Control in the bug title. Severity: S3 (user cannot interact with a control by voice command, but workarounds exist). access keyword: required.

Example 8 — VPN panel not announced when tabbing with VoiceOver

Bug: 2036874 · Core, Disability Access APIs · macOS Category: Platform-specific — macOS platform tree represents non-native popovers incorrectly; fix required restructuring how popup windows appear in the macOS accessibility tree

Before you open any tool

Q1 — What did the user report? When using VoiceOver on macOS and pressing Tab to navigate through the IP Protection / VPN panel in Firefox, VoiceOver stops announcing the panel content. The panel is reachable with Tab (keyboard focus arrives there), but VoiceOver is silent — it does not read the panel’s heading, buttons, or content.

Q2 — AT and OS? VoiceOver on macOS.

Q3 — Focus management bug? No. The user can Tab to the panel — keyboard focus is not lost. The issue is that VoiceOver doesn’t announce what is there. This is an announcement and tree-exposure issue, not a focus management issue.

Q4 — Hypothesis: If this is a generic bug, the VPN panel node or its contents will be absent from the core tree. If the panel IS in the core tree, the failure is in the macOS platform layer.

Step 1: Check the core a11y tree

Self-check answer: I am looking for the VPN panel node and its content. If absent → generic. If present with correct structure → not generic.

What I found: The VPN panel node is present in the core tree. Its child nodes — headings, toggle buttons, status text — are all present with correct names and roles.

Decision: all properties correct → not generic. Continue to Step 2.

Why not stop: The panel and its contents exist in the core tree. The markup is not the problem. Something in the macOS-specific stack is failing to expose the panel in a way VoiceOver can consume.

Step 2: Test with a secondary AT on the same platform

A note specific to macOS: VoiceOver is the only screen reader on macOS. There is no second screen reader to compare with directly. The secondary AT test on macOS uses Voice Control — not because VC reads out content like a screen reader does, but because VC also queries the macOS platform tree to build its numbers overlay. If VC also cannot interact with the VPN panel’s controls, both ATs are failing to read from the same defective macOS platform tree.

Self-check answer: If Voice Control also fails to number any interactive controls inside the VPN panel, both ATs are reading the same broken platform tree. If Voice Control CAN number them, the problem is specific to how VoiceOver navigates.

What I found: Say “show numbers” over the VPN panel. No numbers appear over the panel’s buttons and toggles. Voice Control also cannot interact with the panel’s content.

Decision: second AT also fails → platform-specific.

Why both failing means platform: VoiceOver and Voice Control both read from the macOS platform tree, but via different APIs. When both fail, the platform tree itself is the problem — not either AT’s specific query logic. The root cause turned out to be that non-native popover windows were being structured as children of the root application node in the macOS platform tree, which neither VoiceOver nor Voice Control could navigate into correctly.

Why not AT-specific: If only VoiceOver failed and Voice Control could still interact with the panel, we would conclude VC’s tree was intact and VO was at fault. But both failing eliminates that explanation.

Step 3 — considered and skipped

We could test on Windows with NVDA to confirm that Windows is unaffected and the bug is macOS-only. However, the root cause — AXPopover windows appearing as children of the root application node — is a macOS-specific accessibility API concept. There is no equivalent structure on Windows or Linux. There is no reason to believe the same structural mistake was made in the Windows platform tree.

Decision: skip Step 3. File as macOS, no AT specified.

Why skip: The technical cause is macOS-specific by nature. We have enough information to file accurately without testing Windows. Testing it would not change the scope of the bug or the fix.

Filing

Scope: macOS, no AT in the bug title. access keyword: required.

A note on Steps 2 and 3

Examples 1–6 above all resolve at Step 1 or at Focus Management Testing. This is the typical outcome for bugs discovered through Fable tests and AT audits: the failure is in the markup, the core tree reflects it, and there is no need to continue.

Examples 7 and 8 show the less common cases where the core tree is correct. In Example 7, a second AT on the same platform succeeded — confirming the bug is AT-specific and stopping there. In Example 8, both ATs on the same platform failed — confirming the bug is in the macOS platform tree, and Step 3 was skipped because the cause was macOS-specific by design.

The diagnostic question is always the same: does the core tree have what the AT needs? If yes, keep testing downward. If no, stop — the fix belongs in the markup.
