Bug Verification and Filing — Revised

Purpose of this section

When you find a potential bug in AT testing, your job is to answer one question before filing: Is this a generic bug (affects every platform) or is it specific to a platform or AT? Your answer determines how you file and what scope you assign.

The steps below are a decision tree, not a checklist. Each step is designed to give you enough information to either stop or continue. You should not take a step unless the result of the previous step tells you to continue. If you reach a stopping point, stop — even if you haven’t completed every step in the list.

Before you open any tool

This is the most critical part of the process. Do not open DevTools, the accessibility inspector, or any AT until you have completed this section.

Answer the following in writing (or out loud):

1. What exactly did the user report they could not do? Write it as a single concrete sentence describing the behavior, not the bug. For example: “The user said ‘show numbers’ and the Recent Activity toggle did not receive a number, but the toggles above it did.” Avoid framing it as a bug conclusion at this stage.

2. What AT and OS did they use?

3. Is this a keyboard focus management bug? Signs of a focus management bug: the user pressed a button, submitted a form, or closed a dialog — and then could not find focus, Tab took them nowhere, or focus landed somewhere unexpected. If yes → skip the a11y tree inspection entirely and go to Focus Management Testing.

Signs this is NOT a focus management bug: the user is describing something they heard (or didn’t hear) from their AT about a specific element — a label, a state, a role, a value — or they cannot locate a control at all. These are tree and announcement issues. Continue below.

4. If this is not a focus management bug: what would I expect to find in the core a11y tree if this is a generic bug? Use the reference table below to answer this. Write your answer before looking at anything.

Self-check: Can you describe specifically what would be absent, wrong, or unexpected in the core tree if the bug is generic? If you cannot answer this, re-read the table below before proceeding. Inspecting without a hypothesis means you may find unrelated issues or draw the wrong conclusion.

Focus Management Testing

Reach this section only if Question 3 above indicated a focus management bug.

The a11y tree does not tell you about focus management. The tree describes properties of nodes — not where focus lands after events fire. Inspecting the tree for a focus management bug will not produce useful information and may lead you to draw unrelated conclusions.

Before you test

Self-check: What was the exact action that caused focus to break? Where would you expect focus to land after that action? State both before you test.

  • Buttons that remove or delete an item → focus should move to the next item in the list, or to the parent container if none remain.
  • Buttons that toggle a state (on/off) → focus should remain on the button.
  • Dialogs or panels that close → focus should return to the element that opened them.

How to test

Step A — Reproduce with keyboard only, no AT active.

  • If focus is lost or lands in the wrong place with keyboard only → the bug is in the code, not in the AT. It affects all keyboard-reliant users, including all screen reader users. This is a generic bug. File as Desktop. Stop here.
  • If keyboard-only navigation is fine → the problem is introduced by the AT. Continue to Step B.

Step B — Reproduce with the reported AT. Then test a second AT on the same platform.

Apply the same logic as Steps 2 and 3 in the main flow:

  • If the second AT also causes the focus problem → platform-specific bug.
  • If only the first AT causes the focus problem → AT-specific bug.

Step 1: Check the core a11y tree

Reach this section for tree and announcement bugs — everything except focus management.

Tool: DevTools (web content) or Browser Toolbox (browser chrome) → Accessibility panel.

Important: Go directly to the Accessibility panel — not the DOM markup tab. The DOM can be misleading, particularly with web components: aria-labelledby may reference a valid element ID in the outer DOM that is inaccessible from inside a shadow DOM. The a11y panel reflects computed values and is more authoritative.

Before you look

Self-check: Based on your hypothesis from “Before you open any tool,” state exactly what you are looking for before you open the inspector. Be specific:

  • For a missing-name bug: which field will be empty? (name)
  • For a missing-state bug: which property will be absent? (aria-expanded, aria-pressed, aria-checked, etc.)
  • For a missing-value bug: which field or property will be absent or on the wrong element?
  • For a hidden-element bug: will the element appear in the tree at all, and does aria-hidden or similar appear anywhere on it or its ancestors?

If the bug is about something the user couldn’t find, you are looking for an absence. If it is about something that shouldn’t be there, you are looking for an unwanted presence.

Find the element the user described. Look only at the properties your hypothesis identified.

What you find → what it means

The relevant node or property is absent from the core tree. If it is not in the core tree, no AT on any platform will ever access it. There is no need to test on other platforms or with other ATs. → File as generic (Desktop). Stop here.

The node is present, but the relevant property has an incorrect or insufficient value — a name that exists but lacks context, a role that is wrong or generic, a state attribute that is present but set to the wrong value. Every AT that reads this core tree will receive the same incorrect information. The fix is in the markup. → File as generic (Desktop). Stop here.

The element is present in the core tree when it should be hidden — no aria-hidden or equivalent is applied. Every AT on every platform will be able to reach this element because nothing in the core tree marks it as hidden. → File as generic (Desktop). Stop here.

The node is present and all relevant properties look correct. Something downstream — in the platform tree or AT-specific layer — is failing to expose or consume this information. The core tree is not the source of the bug. → Continue to Step 2.

Note: you may notice other issues while inspecting. Note them separately as potential additional bugs. Do not change your diagnosis for the current bug based on unrelated findings.

Step 2: Test with a secondary AT on the same platform

You have confirmed the core tree is correct. Now determine: is this a failure of the platform tree (shared by all ATs on this OS) or specific to one AT’s interaction with that tree?

Choose a second AT on the same platform and reproduce the same steps.

  • Primary bug is Mac Voice Control → test with VoiceOver
  • Primary bug is Voice Access (Windows) → test with Narrator

Before you test

Self-check: If the second AT also fails, what does that tell you about where in the stack the problem is? If the second AT succeeds, what does that tell you? Write your predictions before you start.

What you find → what it means

The second AT can reach or interact with the item successfully. Both ATs share the same platform tree but query it differently. If one succeeds and one fails, the platform tree is intact — only the first AT’s query of that tree is failing. → File with OS and AT name in the bug title. Stop here. Do not test on another platform.

The second AT also fails. Both ATs are failing because the platform tree itself is built incorrectly from the core tree. → File with OS only (no AT in the bug title). Consider Step 3 only if you have a specific reason to believe the bug affects multiple platforms.

Step 3: Test on a secondary platform

This step is rarely necessary. Reach it only if both ATs on the primary platform failed in Step 2, and you have a reason to believe the error may have been made in multiple platform trees.

If the core tree is correct, the same implementation mistake is unlikely to appear independently in both the Mac and Windows platform trees. You should be able to articulate a specific reason for proceeding here — “I want to be thorough” is not sufficient.

Self-check: Why do I believe this might affect another platform? Is there something about the nature of this markup error that would cause it to appear in multiple platform trees?

What you find → what it means

The bug reproduces on the secondary platform. Note both platforms in the bug report.

The bug does not reproduce on the secondary platform. File as platform-specific to the first OS.

Filing

Scope and field values

DiagnosisOS fieldBug title
Generic (core tree missing, wrong, or element present when hidden; or focus mgmt repros keyboard-only)“Desktop”No OS or AT specified
Platform-specific (both ATs fail; core tree was correct)e.g. “macOS”No AT in title
AT-specific (second AT succeeds; core tree was correct)e.g. “macOS”Include AT in title, e.g. “[macOS] [Voice Control] …”

Always note the platform and AT that reproduced the bug

Include the OS and AT in the STR or environment field regardless of scope. This helps engineers reproduce the issue and confirms you tested in a real environment. If you tested with multiple ATs on the same platform, you should list this and list your findings. For example:

  • I tested with VoiceControl and VoiceOver, but only VO reproduces the issue. VC’s behaviour matches the ‘expected’ section of my STR.
  • I tested with both NVDA and Voice Access. Neither of them can reach the settings toggle.

For bugs filed outside “Disability Access” or “Disability Access APIs” modules

  • Always add the access keyword.
  • Always provide an Accessibility Severity (access-s1 through access-s4).
  • Do not set the Severity or Priority fields unless the owning team explicitly requests it.
